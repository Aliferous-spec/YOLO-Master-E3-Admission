# 开销测量方案与风险降级

## 1. 开销测量方案（已实测）

1. **对照组设计**：同一模型、同一批数据，分别在“开启 hook 采集”与“关闭 hook”两种状态下跑 N 次前向，用 `time.perf_counter()` 记录总耗时。
2. **测量口径**：只测前向 + hook 回调耗时，不含数据加载和后处理。
3. **验收标准**：额外开销占比 = (开 hook 耗时 − 关 hook 耗时) / 关 hook 耗时，目标 < 10%。
4. **实测结果**：`scripts/measure_routing_hook_overhead.py`（yolo-master-n @ 640×640，50 次前向）：本机此前一次测量为关 hook 77.6 ms/次、开 hook 78.7 ms/次（**1.50%**）；8.25 两次复跑分别测得 **2.55%** 与 **-5.01%**（负值来自运行噪声），全部满足 < 10% 目标。
5. **边界**：该数值是 Smoke 单机单次观察，不替代 P1 要求的严格 on/off、warm-up、重复测量与置信区间。

## 2. 风险与降级

- **风险1**：Latent 字段数量（约 35 个）远超 MoE/MoT，若三类强行统一为同一张表会有大量空值列，可读性差。
  → **降级**：采用“公共字段 + 各类专属字段”两层结构，而非单一扁平表。
- **风险2**：当前验证均为未训练模型（随机权重），坍塌现象是否为训练前特有还是训练后依然存在，尚未验证。
  → 后续需在真实训练 checkpoint 上复测。
- **风险3**：MoE 侧依赖 `ExpertUsageTracker` 的 hook 机制，与 MoT/Latent 原生 `last_routing_snapshot` 属性机制不是同一套实现路径。
  → 统一采集层需要做适配层（adapter），而非假设三类接口一致。
- **风险4**：若开销超标，优先降级为“仅静态快照（forward 后一次性读取），不做逐 step 实时记录”，放弃实时面板，保留离线分析能力。
- **风险5**：coco8 为极小数据集，Smoke 只证明采集链路可用，不用于判断训练后路由质量或模型精度。
  → 后续结论必须以训练后 checkpoint + 更大验证集为准。

## 3. 失败时的可执行降级路径

1. 基线环境不可用 → 检查 `BASELINE_PY` / `BASELINE_ROOT`，按 README 安装部署环境后重跑 `run_smoke.cmd`。
2. 单族采集失败 → 在 `summary.json` 中该族标记 FAIL 并保留原始日志，不影响其他族证据；修复后重跑只覆盖失败族。
3. 开销超标（>10%）→ 降级为静态快照模式（见风险4），并在 summary 中记录降级原因。
4. 统一 schema 无法在截止前收敛 → 先按三族分文件交付并明确 `unsupported` 字段，再提交 P0 schema 设计稿。
